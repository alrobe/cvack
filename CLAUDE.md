# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CVack is a vanilla HTML/CSS/JS CV/resume builder with no backend, no build step, and no dependencies (no `package.json`, no npm, no bundler).

## Commands

Run through a local server — opening the HTML files via `file://` breaks JavaScript functionality (module-like restrictions on some browsers, FileReader/photo upload issues):

```bash
python -m http.server 8000
# or: python3 -m http.server 8000
```

Then visit `http://localhost:8000`. There is no build, lint, or test tooling in this repo.

Deployed via GitHub Pages (branch `main`, root) at `https://cvack.arobasoft.com`, configured by the `CNAME` file plus a DNS CNAME record `cvack` → `alrobe.github.io` at Hostinger. The old `https://alrobe.github.io/cvack/` URL 301-redirects there. Since `localStorage` is per-origin, CVs saved under the old URL do not carry over automatically (users can restore from Google Drive or re-import JSON).

## Architecture

- `index.html` — home page linking to the two CV editors (`cv-general.html`, `cv-dev.html`), styled by `css/home.css`.
- `cv-general.html` + `js/general.js` — general-purpose CV editor.
- `cv-dev.html` + `js/script.js` — developer-focused CV editor (adds technologies/tools/framework/version control/project fields to employment entries).
- `css/styles.css` — shared styles for both editors' layout, forms, A4 preview paper, and print rules.
- `privacy.html`, styled by `css/legal.css` — standalone privacy policy page, linked from the home page footer and required by Google's OAuth branding settings / brand verification (see "Google Drive backup" below).
- `css/base.css` — CSS loaded before every page's own stylesheet (via its own `<link>` tag in each HTML file, since there's no build step to `@import` or bundle it). Holds only what's identical across `home.css`/`styles.css`/`legal.css`: the `:root` color variables, the `*`/`html,body`/`body` reset, and the full `.top`/`.logo`/`.logo b` header (every page uses the same 64px/18px sizing, sticky positioning, and `justify-content: space-between` — harmless no-ops on the single-child headers). Each page's own stylesheet keeps only what's genuinely its own (e.g. the editors' `@media(max-width:650px)` rule that stacks their 5 header buttons — home/privacy have their own, different, simpler breakpoints for the same reason: no build step to share it any other way, so check `base.css` before adding a new color variable, reset rule, or `.top`/`.logo` tweak to avoid re-duplicating it across the three page stylesheets).
- `js/common.js` — loaded via its own `<script>` tag before `general.js`/`script.js` in both editor HTML files (same reasoning as `base.css`: no bundler, so a classic script + load order is how sharing works; a later `<script>` tag shares the same global scope as an earlier one). Holds everything that was byte-for-byte identical between the two editors: `esc`/`save`/`toast`, the rich-text sanitizer (`sanitizeHTML`/`toRichHTML`/`RTE_ALLOWED_TAGS`/`getVal`), `field`/`richField`/`itemButtons`, the `edu`/`skill`/`lang` render functions, `move`, the skill/language dot-indicator functions (`dots`/`langDots`), the contact-icon SVG constants, `getResumeFileName`/`download`/`exportJSON`/`importJSON`, `bindCommon()` (the generic `data-*` wiring), and the entire Google Drive backup block. It assumes `empty`, `ARRAY_FIELDS`, `ITEM_TEMPLATES`, `data`, `render()`, and `preview()` are declared by whichever page-specific script loads after it — safe because those are only referenced *inside* `common.js`'s functions, not at its own top level, so they don't need to exist yet when `common.js` itself runs, only by the time something actually calls into it.

`general.js` and `script.js` keep only what's genuinely specific to their CV type: `CV_TYPE`/`SCHEMA_VERSION` (see schema versioning below — note these two must be declared *before* `empty`, unlike the rest of this per-file-constant pattern, because they're used as literal values inside the `empty` object itself, which evaluates immediately, not just referenced later inside a function body), the `empty` schema, `ARRAY_FIELDS` (the list of top-level array keys — general.js's includes `"hobbies"`, script.js's doesn't), `ITEM_TEMPLATES` (one object per array field, defining exactly which keys and defaults a single item — an employment entry, a skill, etc. — is allowed to have; script.js's `employment` template has 6 extra keys the dev CV needs), `MIGRATIONS` (per-file, since general/dev schemas could diverge independently in the future — see schema versioning below), `render()` (the personal-details field list differs), `job()` (the dev CV has 6 extra fields), the schema-specific parts of `bind()` (the `addJob` initial object — pushed via `structuredClone(ITEM_TEMPLATES.employment)` — and general.js's hobbies wiring; `bindCommon()` from `common.js` handles everything else, including `addEdu`/`addSkill`/`addLang` via the same templates), and `preview()` (the `<main>` content and contact-fallback text differ). A fix or feature added to one of these page-specific pieces must still be manually ported to the other if it should apply to both — but anything already in `common.js` only needs fixing once.

`data` is always schema-clean, no matter how it got populated: `sanitizeData(raw)` (in `common.js`) uses `pickFields(obj, template)` to rebuild `personal` and every item of every `ARRAY_FIELDS` array key-by-key against `empty.personal`/`ITEM_TEMPLATES`, rather than spreading the raw object directly. Any field not in the schema (a stray top-level key, an extra key inside `personal` or inside an employment/education/skill/language entry) is silently dropped — otherwise it would get persisted to `localStorage` and re-uploaded on every Google Drive backup. Hobbies (plain strings, no object template) are coerced with `String(item ?? "")` instead, so a non-string entry can't sneak in as an object. Both `importJSON()` and the page's own initial `let data = sanitizeData(JSON.parse(localStorage.getItem(STORAGE_KEY) || "null")); localStorage.setItem(STORAGE_KEY, JSON.stringify(data));` load route through it, so `localStorage` itself gets rewritten clean immediately on page load (not just after the next edit) even if it was holding junk from before this sanitization existed.

The JSON schema is self-describing and versioned via two fields deliberately placed first in `empty` (so they're also first in every `JSON.stringify(data)` output — export, Drive backup): `cvType` (`"general"` / `"dev"`, from each file's own `CV_TYPE` constant) and `schemaVersion` (from each file's own `SCHEMA_VERSION` constant, currently `1` in both — today's shape *is* version 1). `sanitizeData()` runs `raw` through `runMigrations(raw)` first: it reads `raw.schemaVersion` (treating a missing one as already-current, since that's just pre-this-feature legacy data with today's shape) and walks forward applying whatever's registered in that file's own `MIGRATIONS` object (keyed by the version being migrated *from*; currently empty in both files — no real migration exists yet, this is purely the plumbing for the next schema change) until it reaches `SCHEMA_VERSION`, then stamps `raw.schemaVersion = SCHEMA_VERSION` before `pickFields` runs. `sanitizeData()` also force-sets `result.cvType = CV_TYPE` at the end — same "never trust the imported shape" reasoning as `STORAGE_KEY`/`ARRAY_FIELDS`/`ITEM_TEMPLATES`; an imported file's own `cvType` is only ever read pre-sanitize for the check below, never carried into the final `data`. `importJSON()` uses that pre-sanitize read to warn on a cross-type import (including a JSON with no `cvType` at all, treated the same as a mismatch per explicit product decision): a `confirm()` naming the mismatch, and returning early (no `sanitizeData` call, no `localStorage` write) if the user cancels — this applies identically to the plain "Import Json" file picker and to "Restore from Google", since both already funnel through this one function.

Each script defines its own `STORAGE_KEY` (`cvack-general` / `cvack-dev`, used by `common.js`'s `save()`/`importJSON()` and by the page's own initial `data` load), plus its own `DRIVE_BACKUP_NAME` and `DRIVE_FILE_ID_KEY` (see "Google Drive backup" below), so the two CV types no longer share saved data or collide on the same Drive backup file. The OAuth access token cache (`orange-cv-drive-token`) is the one thing still intentionally shared — it's tied to the Google session, not to CV data, so reusing it across both editors just avoids an extra login popup.

All user-provided text rendered into the DOM must go through the `esc()` helper (HTML-escaping) to avoid XSS, since both `render()` and `preview()` build HTML via template-string interpolation.

## Google Drive backup

Both editors have "Back up with Google" and "Restore from Google" buttons backed by a shared block at the end of `js/common.js` (see "Architecture" above). It uses Google Identity Services (`https://accounts.google.com/gsi/client`, loaded via `<script>` tag in each HTML file) to get an OAuth access token client-side (no backend, no client secret — `GOOGLE_CLIENT_ID` is public and safe to commit) with the `drive.appdata` scope, then reads/writes `data` as JSON directly against the Drive API v3 via `fetch`, in the user's hidden Application Data folder (`parents: ["appDataFolder"]` on create).

- The backup file is invisible in the user's normal Drive UI and only reachable through this app (or a full Google Takeout export) — this was a deliberate choice over the visible `drive.file` scope, since the app already offers "Export Json" for a user-manageable copy.
- `requestDriveAccessToken(onToken)` lazily creates a single shared `driveTokenClient` (via `initTokenClient`) and reassigns its `.callback` per call before invoking `requestAccessToken()` — this is how one token client is reused for both the backup (`uploadBackupToDrive`) and restore (`downloadBackupFromDrive`) flows instead of hardcoding the callback at init time.
- The resolved OAuth access token is cached in `sessionStorage` (key `orange-cv-drive-token`, tab-scoped, cleared when the tab closes) with its expiry, so repeated backup/restore clicks within the same token lifetime (~1h) skip Google's login/consent popup entirely. A `401` response from Drive clears this cache and asks the user to retry, which triggers a fresh popup on the next click — there is no real refresh token in this client-only flow (that requires a backend holding a client secret), so a new login is unavoidable once the cached token expires or the tab is closed.
- The Drive file id is cached in `localStorage` under a per-CV-type key (`DRIVE_FILE_ID_KEY`, e.g. `cvack-general-drive-file-id` / `cvack-dev-drive-file-id`, declared alongside `STORAGE_KEY` in `general.js`/`script.js`); backups `PATCH` that same file instead of creating a new one each time, and restore uses it to `GET .../files/{id}?alt=media` directly. If the id isn't cached (e.g. a new browser/device), both flows fall back to `findDriveBackupFileId()`, which queries `spaces=appDataFolder` by file name (`DRIVE_BACKUP_NAME`, also per-CV-type — `cvack-general.json` / `cvack-dev.json`) ordered by `modifiedTime desc` — this keeps a single backup file per Google account *per CV type* even across browsers, and self-heals by always targeting the newest match if stale duplicate files exist from earlier testing/bugs. A 404 on either path clears the cached id (backup retries as a create; restore just reports the backup is gone).
- Restore reuses the existing `importJSON()` (parses, merges with `empty`, persists to `localStorage`, re-renders) — it's the same code path as the "Import Json" file button, just fed by Drive content instead of a local file. It's gated behind a `confirm()`, matching the "New CV" button's pattern of warning before discarding unsaved local edits.
- `GOOGLE_CLIENT_ID` must be a real OAuth Web Client ID from Google Cloud Console, with the deployed origin `https://cvack.arobasoft.com` (no path) and `http://localhost:8000` registered as Authorized JavaScript origins.
- The `drive.appdata` scope is classified as **non-sensitive** by Google (same tier as `drive.file`), so publishing the OAuth app from "Testing" to "In production" (which lifts the ~100-test-user cap) does not require sensitive-scope review (no demo video or scope justification). Optional brand verification (needed to show the CVack name/logo on the consent screen) requires the homepage and `privacy.html` to be public, the app name to match, and ownership of `arobasoft.com` verified in Google Search Console (a Domain property verified by a DNS TXT record at Hostinger, which covers every `*.arobasoft.com` subdomain, so future apps can reuse it). The OAuth Branding authorized domain is `arobasoft.com`. Adding any sensitive/restricted scope later would trigger full verification.
